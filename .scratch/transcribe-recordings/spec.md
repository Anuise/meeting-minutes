# Spec: Transcribe —— 把 Recording 變成 Note

Status: ready-for-agent

## Problem Statement

使用者手上有會議錄音與錄影，但這個系統收不了。

`rawdata/<meeting>/` 裡放進 `.mp3` / `.mp4` 之類的檔案時，Ingest 會把它們列進 `unsupported` 並回一句「請先自行轉成逐字稿」。流程在「取得逐字稿」這一步斷在系統之外（ADR-0003），使用者得離開這個工具、用別的東西轉錄、把結果貼回 `rawdata/`，才能繼續。

實務上這代表：一場會議留下的最完整、資訊密度最高的素材——錄音——是唯一一種這個系統不處理的素材。而簡報和既有文件反而是次要的。使用者要的會議記錄，主要內容本來就在錄音裡。

ADR-0003 當初排除音訊有兩個理由：markitdown 的轉錄後端對會議長度的錄音不堪用，以及「使用者手邊已有可用的轉錄工具」。第一個理由仍然成立；第二個理由現在失效了——使用者要的是流程不要斷。同時，ADR-0003 明文預留了推翻條件：「需求出現時再開一份新的 ADR 推翻這份。」

現在使用者的內網有一台自建的 ASR Service（FastAPI，非同步分段轉錄，支援中文），需求出現了。

## Solution

新增第四個階段：**Transcribe**，位於 Ingest 之前。

使用者把錄音或錄影原封不動丟進 `rawdata/<meeting>/`，跟其他素材一樣。Transcribe 把它們轉成 mp3、送到內網的 ASR Service、等它轉完、把逐字稿寫成 `notes/<meeting>/` 底下的 Note。之後的 Ingest → Extract → Render 完全不變。

對使用者而言，改變只有一句話：**錄音現在可以直接放進去了。**

Transcribe 分成 Submit 與 Fetch 兩個步驟，因為 ASR Service 是非同步的：Submit 轉檔並上傳、拿回 Transcription Task 的 id；Fetch 查狀態，完成就把逐字稿落成 Note，沒完成就回報進度。等待與判斷留在 agent 端，容器只做確定性的機械工作，與 ADR-0004 一致。

逐字稿不是一整塊文字，而是照 ASR Service 回的分段切成帶時間碼的小節。這讓 Extract 產出的每一筆決議與待辦仍然能有精確的 `source` 行號，也讓使用者拿時間碼回錄音裡查證。

Ingest 本身**不改行為**：它仍然只做 markitdown 的機械轉檔，音訊與影片照樣落在 `unsupported`。改的只是那句訊息——從「請自行轉成逐字稿」變成「交給 Transcribe」。ADR-0003 因此只被推翻一半，Ingest 的定義保持乾淨。

## User Stories

### 放素材

1. 作為會議記錄製作者，我想要把錄音檔直接丟進 `rawdata/<meeting>/`，這樣我不必先跑一趟別的轉錄工具再把結果貼回來。
2. 作為會議記錄製作者，我想要把會議錄影（mp4、mkv 等）也直接丟進去，這樣我不必自己先抽音軌。
3. 作為會議記錄製作者，我想要錄音跟簡報、既有文件混在同一個 `rawdata/<meeting>/` 裡，這樣我對「一場會議的素材放在哪」的心智模型不用改變。
4. 作為會議記錄製作者，我想要放在子資料夾裡的錄音也被找到，這樣我可以照自己的習慣分類素材。
5. 作為會議記錄製作者，我想要我的 Raw Material 一個位元都不被改動，這樣弄丟了就沒有的原始素材永遠安全。

### 轉檔與上傳

6. 作為會議記錄製作者，我想要系統自動把錄音轉成適合上傳的 mp3，這樣我不必知道什麼位元率、幾聲道才適合語音辨識。
7. 作為會議記錄製作者，我想要轉出來的 mp3 明顯小於原始錄影，這樣上傳不會佔滿 ASR Service 只有十幾 GB 的磁碟。
8. 作為會議記錄製作者，我想要 mp3 放在跟 Raw Material 分開的地方，這樣我一眼看得出哪些檔案是我放的、哪些是機器產的。
9. 作為會議記錄製作者，我想要 mp3 隨時可以整個刪掉重建，這樣磁碟不夠時我知道刪哪裡是安全的。
10. 作為會議記錄製作者，我想要上傳前系統先確認 ASR Service 還有空間，這樣我不會傳到一半才發現對方磁碟滿了。
11. 作為會議記錄製作者，我想要檔名有空格或中文的 Meeting 也能正常處理，這樣我不必為了工具而改我的命名習慣。

### 等待與進度

12. 作為會議記錄製作者，我想要上傳完就先拿到一個明確的「已送出」回報，這樣我知道東西確實進去了，不是卡住。
13. 作為會議記錄製作者，我想要在等待期間看得到轉錄進度（百分比、已完成幾段），這樣我知道還要等多久，而不是盯著一個沒有回應的畫面。
14. 作為會議記錄製作者，我想要轉錄超過十分鐘也不會讓流程逾時失敗，這樣一小時以上的會議錄音能正常處理。
15. 作為會議記錄製作者，我想要中途關掉視窗、隔天再回來也接得上，這樣長時間的轉錄不會因為我離開而白做。

### 逐字稿的樣子

16. 作為會議記錄製作者，我想要逐字稿落成一份跟其他 Note 平起平坐的 markdown，這樣後面的 Extract 完全不必為錄音特別處理。
17. 作為會議記錄製作者，我想要逐字稿的 Note 標明它來自哪一個 Recording，這樣我看到 source 引用時查得回原始錄音。
18. 作為會議記錄製作者，我想要逐字稿被切成帶時間碼的小節，這樣 Extract 產出的每筆決議都能指到精確的行號，而不是指向一整團文字。
19. 作為會議記錄製作者，我想要從 Note 上的時間碼能直接回錄音裡聽那一段，這樣別人質疑某條決議時我當場查得到。
20. 作為會議記錄製作者，我想要逐字稿的 Note 記下它是哪一個 Transcription Task 產的，這樣品質有問題時我查得到是哪一次轉錄。

### 失敗與重跑

21. 作為會議記錄製作者，我想要某一段轉錄失敗時 Note 上留下明顯的警語，這樣我不會把「機器沒轉出來」誤讀成「那段沒人講話」。
22. 作為會議記錄製作者，我想要一份錄音失敗不影響同一場會議的其他錄音，這樣整批不會被一個壞檔擋住。
23. 作為會議記錄製作者，我想要整個任務失敗時系統續傳而不是從頭重送，這樣已經轉好的部分不會白費，也不會白燒對方一次運算資源。
24. 作為會議記錄製作者，我想要重跑 Transcribe 是安全的，這樣我不確定跑到哪的時候可以放心再跑一次。
25. 作為會議記錄製作者，我想要已經轉好的 mp3 不會被重轉，這樣重跑不用再等一次轉檔。
26. 作為會議記錄製作者，我想要已經送出的錄音不會被重送，這樣我不會在對方的佇列裡塞出兩份一樣的任務。
27. 作為會議記錄製作者，我想要我手動修過的逐字稿 Note 不會被覆蓋，這樣我校對過的內容不會被機器蓋掉——跟 Ingest 的規則一致。

### 串進主流程

28. 作為會議記錄製作者，我想要 `mm-minutes` 自動處理錄音，這樣我用主要入口就好，不必記得多跑一個步驟。
29. 作為會議記錄製作者，我想要在 Meeting 清單上看得出哪一場有還沒轉錄的錄音，這樣我知道哪些會議還卡著。
30. 作為會議記錄製作者，我想要 Ingest 遇到錄音時的訊息告訴我正確的下一步，這樣我不會照著舊訊息去自己找轉錄工具。
31. 作為會議記錄製作者，我想要沒有錄音的 Meeting 完全不受影響，這樣既有的工作流程一行都不用改。

### 環境與設定

32. 作為維護者，我想要 ASR Service 的位址放在不進 git 的設定裡，這樣內網位址不會被推上去，換環境也不必改程式碼。
33. 作為維護者，我想要位址沒設定時得到一句明確的錯誤，這樣我知道要去設什麼，而不是看到一個連線逾時。
34. 作為維護者，我想要宿主端仍然零安裝，這樣 ADR-0004 的紀律不因為多了 ffmpeg 和 HTTP 呼叫而破功。
35. 作為維護者，我想要關閉 TLS 驗證這件事被寫進 ADR，這樣未來讀者知道那是憑證 SAN 對不上 LAN IP 的結果，不是有人偷懶。

### 領域語言

36. 作為維護者，我想要錄音、mp3、轉錄任務三個新概念各有明確的名字，這樣後續討論不會在「音檔」這種模糊詞上打轉。
37. 作為維護者，我想要 ADR 明白記下推翻了 ADR-0003 的哪一半，這樣未來讀者不會以為 Ingest 現在什麼都吃。

## Implementation Decisions

### 新階段的形狀

- 新增一個 **Transcribe** 階段，位於 Ingest 之前。它把 Recording 變成 Note，**不呼叫模型**——Extract 仍然是唯一呼叫模型的步驟。
- Transcribe 由兩個 CLI 子命令構成：**Submit**（轉檔 + 上傳 + 記錄 Transcription Task）與 **Fetch**（查狀態；完成就寫 Note，未完成就回進度）。
- 拆兩步的理由：ASR Service 是非同步的，把它包成同步只是把非同步藏起來，藏不住的時候（逾時、中斷）代價一次爆出來。拆開之後進度看得到、被中斷不掉任務、重跑天然冪等，而且符合 ADR-0004 的「容器只做確定性機械工作，等待與判斷留在 agent 端」。
- 兩個子命令都吃 Meeting slug、都吐 JSON 到 stdout、都完全非互動，與現有子命令一致。

### 新的領域概念與存放位置

- **Recording**：Raw Material 裡的音訊或影片檔。是唯一需要經過外部服務才能變成 Note 的素材。
- **Media**：Recording 轉出來、實際送去轉錄的 mp3。可拋棄，隨時可從 Recording 重建。放在 `media/<meeting>/`，讀寫掛載。
- **Transcription Task**：ASR Service 上的一個轉錄任務。狀態記在 Media 旁邊的一個 sidecar 檔，與 mp3 同生命週期。
- `rawdata/` **維持唯讀掛載**。唯讀是把「原始素材弄丟就沒了」用機制擋住，不該為了放中繼檔而拆掉。Media 是純衍生物，性質與 Deliverable 相同，因此另立目錄。
- `mm init` 的骨架清單加入 Media 目錄。

### 判定哪些檔案是 Recording

- 沿用 Ingest 現有的那一組判定：寫死的音訊/影片副檔名清單為地板、`mimetypes` 猜出的 `audio/*` 與 `video/*` 補漏。ADR-0003 已經把這組規則定死並寫了測試。
- 把現有那個「回傳不支援訊息」的函式重構成**回傳分類**（音訊/圖片/支援），讓 Ingest 與 Transcribe 共用同一個真實來源。開第二套判定遲早漂移。

### 轉檔

- ffmpeg 裝進現有映像，由 CLI 以子行程呼叫。不另開 compose service——那會把「哪些檔要轉、轉出來叫什麼名字」這類機械判斷推回 agent 端，正是 ADR-0004 想避免的。
- 參數固定，不開放設定：

  ```
  ffmpeg -nostdin -y -i <recording> -vn -ac 1 -ar 16000 -b:a 32k -f mp3 <media>
  ```

  丟視訊、單聲道、16 kHz（Whisper 系模型內部就是這個取樣率，更高只是浪費）、32 kbps（語音夠用，一小時約 14 MB）。
- 以 argv list 傳參、不經 shell——Meeting slug 含空格與中文。
- Media 的檔名 = Recording 在 `rawdata/<meeting>/` 底下的相對路徑 + `.mp3`，**保留原副檔名**。與 Note 的命名規則同一條理由：看得出來源，且同名不同格式的兩份錄音不會互相蓋掉。

### 與 ASR Service 的契約

- 上傳走 **multipart 的建立任務端點**，帶檔案與語言，直接拿回任務摘要。不走可續傳的分塊上傳（tus / WebSocket）：那是另一套協定、另一個服務端點、失敗面加倍，而實測服務端單檔上限 4 GB，遠高於任何一場會議的 mp3。
- 上傳前先查服務端的儲存狀態端點，mp3 超過單檔上限或剩餘空間不足就明確報錯、不送。
- 語言參數**寫死為中文**，不開 CLI flag。專案的會議全是繁中；明確傳而不吃服務端預設，是為了不隨對方版本漂移。
- 逐字稿**從任務詳情端點回的分段陣列組出來**，不用單獨的結果下載端點。分段自帶起訖秒數與文字，那是把時間碼帶進 Note 的唯一來源。
- **不刪除服務端的任務**。刪了本地的 Transcription Task 記錄就指向死 id、狀態不一致，重抓的路也斷掉。改為在回報時附上服務端剩餘空間，資源治理留給使用者。

### 連線與設定

- 服務位址由環境變數提供，值放在不進 git 的設定檔，經 compose 傳進容器。沒設就明確報錯說要去設什麼。
- 位址是環境的屬性，不是命令的屬性——現有子命令的參數全是「這次要處理哪場會議」這種真正的命令參數，位址混進去會破壞那個分界。
- **關閉 TLS 憑證驗證**。服務的憑證是自簽的 `CN=asr-service`，Subject Alternative Name 只有 `localhost` 與 `127.0.0.1`，用 LAN IP 連一定驗不過，而且不是掛 CA 就能解決的那種失敗——那個 IP 根本不在 SAN 裡。連線仍然加密，但無法確認對面是不是預期的那台機器；同網段的 ARP 欺騙能攔下會議錄音。這個取捨連同「憑證修好就把它拿掉」的條件寫進 ADR。
- **不加開關**。現在只有一種情況，加環境變數開關是在猜未來。
- 不需要 host gateway 設定——服務在 LAN IP 上，容器直接連得到。
- 新增一個 HTTP client 依賴。

### Note 的形狀

逐字稿 Note 的結構（時間碼小節是這個決定的核心，不是排版偏好）：

```markdown
# <recording 檔名>（語音轉文字）

- 來源：rawdata/<meeting>/<recording 檔名>
- 任務：ASR Service task <id>（語言 Chinese，時長 <秒> 秒，<n> 段）

## 00:00:00–00:01:30

<這一段的逐字內容>

## 00:01:30–00:03:00

...
```

- 切段的理由是**可查證性**：每筆決議與待辦都要帶 `source`，格式是 Note 路徑加行號。一整塊純文字會讓所有 source 指向同一團，等於失去 ADR-0002 之後整條流程賴以成立的溯源能力。切段後行號自然分散，使用者也能拿時間碼回錄音查證。
- 轉錄失敗的分段**照樣佔一個小節**，內容換成明顯的警語與服務端回的錯誤訊息。空白比警語危險——Extract 會把沒字的那段當成「沒人講話」。

### 冪等與重跑

Submit 是冪等入口，四層跳過，沿用 Ingest 的 mtime 慣例：

| 狀況 | 行為 |
| --- | --- |
| Media 已存在且比 Recording 新 | 不重轉 |
| 沒有 Transcription Task 記錄 | 轉檔 → 上傳 → 寫下記錄 |
| 有記錄、任務進行中或已完成 | 跳過 |
| 有記錄、任務失敗 | 呼叫服務端的續傳端點，不重新上傳 |

Fetch 的跳過規則：Note 已存在且比 Transcription Task 記錄新就不覆寫——使用者可能手動修過逐字稿。這是 Ingest「Note 比 Raw Material 新就跳過」同一條規則的延伸。

**不新增重試命令、不新增重試 flag**：續傳語意由 Submit 承擔。

### 與既有階段的關係

- **Ingest 的行為一行不改**。音訊與影片照樣落在 `unsupported`——Ingest 的定義就是 markitdown 的機械轉檔，把轉錄塞進去會弄髒它。只改那句訊息的內容，指向 Transcribe。
- 因此 **ADR-0003 只被推翻一半**：Ingest 仍然不碰音訊，改由 Transcribe 處理。這比讓 Ingest 什麼都做乾淨得多。
- Meeting 清單多一個「有沒有 Recording 還沒轉成 Note」的狀態。
- 主流程（`mm-minutes`）在 Ingest 之前插入 Transcribe：Submit → 定期 Fetch 並回報進度 → 全部完成才往下。
- 新增一個與 Ingest 對稱的 Transcribe skill；Ingest、主流程、清單三個 skill 的文件同步更新。

### 文件

- 領域語言新增 Recording、Media、Transcription Task 三個名詞與 Transcribe 一個動作；Raw Material 的定義拿掉「不含音訊」，改為指向新的 ADR。圖片仍然排除（ADR-0005 不動）。
- 新增 ADR，標明部分取代 ADR-0003。要記下五件未來讀者會困惑的事：推翻 ADR-0003 的條件如何成立、為何 `rawdata/` 仍唯讀而 Media 另放、**為何關閉 TLS 驗證**、為何選 multipart 而非可續傳上傳、為何拆 Submit / Fetch 兩步。

## Testing Decisions

### 什麼是好的測試

只測外部行為，不測實作細節。這個 repo 既有的六份測試已經定了調：起一個 `tmp_path` 骨架、以子行程跑一次真的 CLI 子命令、斷言**檔案系統的結果**與 **stdout 的 JSON**。沒有一份測試 import 被測模組的內部函式。新測試照這個形狀寫。

### Seam

**兩個，一個沿用一個新增。**

1. **CLI 子行程（沿用）** —— 與 `test_ingest.py`、`test_render.py`、`test_check.py` 完全相同的形狀。這是最高的 seam，也是既有的唯一 seam。
2. **ASR Service 的 HTTP 邊界（新增）** —— pytest fixture 用標準函式庫的 HTTP server 起一個假服務，靠環境變數把 CLI 指過去。這是能取的最高點：不 patch HTTP client、不注入 client 物件、不引入 mock 框架。測試看到的仍然只有「跑一次真 CLI、看檔案和 JSON」。

ffmpeg **不是新 seam**：容器裡裝了真的，直接跑。測試素材用 ffmpeg 自己產一段極短的靜音，真的轉一次、驗 mp3 出得來。比假造轉檔誠實，成本也低。

### 要測的行為

- Submit：Recording 被找到（含子資料夾）、Media 產出、Transcription Task 記錄寫下、非 Recording 的素材不受影響。
- Submit 的四層冪等：Media 新於 Recording 就不重轉、已有進行中的任務就不重送、失敗的任務走續傳而非重傳。
- Fetch：逐字稿落成 Note、時間碼小節切得對、來源與任務資訊出現在 Note 開頭。
- Fetch 的未完成路徑：回報進度而不寫 Note。
- 分段失敗：Note 上留下警語而非空白。
- 一份 Recording 失敗不影響同一場的其他 Recording。
- Note 新於 Transcription Task 記錄就不覆寫。
- 服務端空間不足或超過單檔上限時明確報錯、不上傳。
- 位址環境變數未設定時明確報錯。
- **`rawdata/` 一個位元都沒被寫過**——照抄 `test_ingest.py` 既有的雜湊快照手法，涵蓋新流程。
- Ingest 對音訊的訊息改了之後仍然把它們列進 `unsupported`、仍然不留下 Note。

### Prior art

- `tests/test_ingest.py` —— 子行程跑 CLI、四個結果清單的斷言、mtime 跳過規則、`rawdata/` 雜湊快照。新測試的主要參照。
- `tests/fixtures.py` —— 每種格式一個小 fixture 的寫法。靜音音檔的 fixture 加在這裡。
- `tests/test_list.py` —— 清單新增欄位的斷言形狀。

## Out of Scope

- **可續傳上傳**（tus / WebSocket）。實測單檔上限 4 GB，遠高於任何一場會議的 mp3；斷線重傳的成本只是再等幾分鐘。真的碰到需要時另開 ADR。
- **講者分離**。ASR Service 的契約沒有提供，Note 上不會有「誰講的」。
- **多語言**。語言寫死中文。
- **自動清理服務端的任務**。
- **圖片**。ADR-0005 不動，白板照仍然需要使用者自己補一份文字說明。
- **本地轉錄**（faster-whisper 之類）。這份 spec 只接既有的內網服務。
- **TLS 憑證修復**。屬於 ASR Service 那一側；這邊只記下取捨與拿掉關閉驗證的條件。
- **Transcribe 的進度推播**。進度靠 agent 端定期 Fetch 取得，不做長連線。

## Further Notes

### 三件要在第一次真跑時確認的事（已探明）

契約文件沒說死，票 04 以一份 15 秒的中文錄音對真服務跑過一次，結果如下：

1. **分段的文字欄位真的回填。** 任務詳情端點回的 `chunks[].text` 帶著逐字內容，`start_sec` / `end_sec` 也都有值。時間碼小節這條路走得通，不需要改用結果下載端點。
2. **任務狀態的值域**：`pending`（建立當下）→ `preprocessing` → `done`。轉錄不了的檔案落在 `failed`，`error_message` 帶服務端的 ffmpeg 訊息。分段自己的 `status` 見到 `done`。冪等規則因此以 `failed` 為續傳的判準、其餘一律跳過。
3. **上傳檔名可以帶中文與空格。** 送 `20260805 探測 錄音.wav` 進去，`original_filename` 原樣回來，UTF-8 沒有被改寫。實作仍然只送 Media 的檔名（不含路徑分隔字元）——斜線在服務端怎麼處理沒探明，而對應關係的真實來源本來就是本地的 Transcription Task 記錄。

### 規模與成本

- 映像因為 ffmpeg 增加約 150 MB，需要重新 build。ADR-0004 早就記下「改依賴要記得手動 rebuild」。
- 一小時會議的 mp3 約 14 MB，三小時約 43 MB。實測服務端剩餘空間約 15 GB——這是**不傳原始錄影而先轉 mp3 的主要理由**，幾場未轉檔的錄影就能吃光對方磁碟。
- 轉錄時間可能遠超過十分鐘，這正是拆 Submit / Fetch 的直接原因。

### 已探明的服務端事實

- 服務健康、模型已載入、**無任何認證**。
- 單檔上限 4096 MB。
- 只有 HTTPS，明文 port 不通。
- 憑證自簽，SAN 只涵蓋 `localhost` 與 `127.0.0.1`。
