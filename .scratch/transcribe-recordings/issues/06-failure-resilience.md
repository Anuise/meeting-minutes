# 06 — 失敗韌性

**What to build:** 三種失敗不再讓使用者吃虧或被誤導。

某一段轉錄失敗時，Note 上那個位置留下顯眼的警語與服務端回的錯誤訊息，而不是一片空白——**空白比警語危險**，Extract 會把沒字的那段當成「那時候沒人講話」，於是一段真的有內容的討論被安靜地漏掉。

整份任務失敗時，重跑 Submit 走服務端的續傳而不是從頭重送，已經轉好的部分不白費，也不白燒對方一次運算資源。續傳語意由 Submit 承擔，**不新增重試命令、不新增重試 flag**。

一份錄音壞掉不擋住同一場會議的其他錄音，整批照跑完，失敗項目集中回報——與 Ingest 的既有規矩一致。

**Blocked by:** 04、05

**Status:** ready-for-agent

- [ ] 失敗的分段照樣在 Note 上佔一個帶時間碼的小節，內容換成顯眼的警語與服務端的錯誤訊息
- [ ] Fetch 的 JSON 把有失敗分段的 Note 列出來，不安靜吞掉
- [ ] Submit 遇到已有記錄但任務失敗時呼叫服務端的續傳端點，**不重新上傳** mp3
- [ ] 續傳後的狀態回寫進本地的 Transcription Task 記錄
- [ ] 一份 Recording 在任一步失敗（轉檔、上傳、續傳、取回）都不中斷整批
- [ ] 只要命令跑得起來就 exit 0，失敗項目在 JSON 裡——與 Ingest 一致，呼叫端不能只看 exit code
- [ ] 測試涵蓋：分段失敗留下警語而非空白、失敗任務走續傳而非重傳、單一 Recording 失敗不擋批
