# 經由內網 ASR Service 轉錄 Recording

**部分取代 ADR-0003。** 被推翻的只有「Raw Material 不收音訊」這一半：錄音與錄影現在可以直接放進 `rawdata/<meeting>/`，由新的 Transcribe 階段變成 Note。**Ingest 仍然不碰音訊**——它遇到 Recording 照樣列進 `unsupported`，只是訊息改成指向 Transcribe。

## 推翻的條件如何成立

ADR-0003 自己寫下了推翻條件：「決定先不做，需求出現時再開一份新的 ADR 推翻這份。」當初排除音訊有兩個理由，現在一個仍然成立、一個失效了：

- **markitdown 的轉錄後端對會議長度的錄音不堪用**——仍然成立。這份 ADR 不動用 markitdown 的 `audio-transcription` extra，映像照樣不裝它。
- **「使用者手邊已有可用的轉錄工具」**——失效。使用者要的是流程不要斷在系統之外：一場會議留下的最完整、資訊密度最高的素材就是錄音，卻是唯一一種這個系統不處理的素材。

同時，使用者的內網出現了一台自建的 ASR Service（FastAPI，非同步分段轉錄，支援中文，無認證）。需求與手段同時到位。

## 為什麼 Ingest 不一起改

Ingest 的定義是 markitdown 的機械轉檔。把「呼叫外部服務、等它幾十分鐘、組出時間碼小節」塞進去，會讓一個原本一句話講得完的階段變成兩種完全不同的東西。新增第四個階段比弄髒既有的那個乾淨。

代價是使用者對同一批 Recording 會看到兩種說法（Ingest 說「不支援」、Transcribe 說「已送出」）。這由訊息文字承擔：Ingest 的 `unsupported` 訊息指向 Transcribe，那是使用者唯一看得到「只被推翻一半」的地方。

## 為什麼 `rawdata/` 仍維持唯讀，Media 另立目錄

`rawdata/` 唯讀是用機制擋住「原始素材弄丟就沒了」（ADR-0004）。為了放一個隨時能重建的衍生檔而把它拆成讀寫，等於用一個永久的風險換一個暫時的方便。

Media（送去轉錄的 mp3）是純衍生物，性質與 Deliverable 相同：可拋棄、隨時可從 Recording 重建、磁碟不夠時刪掉是安全的。因此另立 `media/<meeting>/`，讀寫掛載，並列入版控忽略清單。Transcription Task 的記錄放在 Media 旁邊，與 mp3 同生命週期——刪掉 Media 就等於放棄那次轉錄，兩者一起消失才不會留下指向死 id 的孤兒記錄。

## 為什麼關閉 TLS 憑證驗證

ASR Service 的憑證是自簽的 `CN=asr-service`，Subject Alternative Name 只涵蓋 `localhost` 與 `127.0.0.1`。我們用 LAN IP 連它，**驗證一定過不了，而且不是把 CA 掛進信任庫就能解決的那種失敗**——那個 IP 根本不在 SAN 裡。服務只開 HTTPS，明文 port 不通，所以也沒有「先不加密」這個選項。

取捨講白：連線仍然加密，但**無法確認對面是不是預期的那台機器**。同網段的 ARP 欺騙能攔下整場會議的錄音。這是在內網、無認證的服務前提下接受的風險。

**拿掉的條件**：ASR Service 換上一張 SAN 涵蓋其 LAN IP（或改用一個解析得到的主機名）的憑證之後，就把關閉驗證的那一行拿掉。憑證修復屬於 ASR Service 那一側，不在這個 repo 的範圍。

**不加開關。** 現在只有一種情況，加一個環境變數開關是在猜未來，而且會讓「什麼時候是驗證的」變成執行期才知道的事。

## 為什麼選 multipart 而不是可續傳的分塊上傳

服務端另有一組可續傳的分塊上傳端點（tus / WebSocket）。不用它：

- 那是另一套協定、另一組端點、另一份狀態機，失敗面加倍。
- 實測服務端單檔上限 4096 MB，而一小時會議的 mp3 約 14 MB、三小時約 43 MB——差三個數量級。
- 斷線重傳的成本只是再等幾分鐘。真的碰到需要時另開一份 ADR。

## 為什麼把 Transcribe 拆成 Submit 與 Fetch 兩步

ASR Service 是非同步的。把它包成一個同步命令只是把非同步藏起來，而藏不住的時候（逾時、使用者關掉視窗）代價會一次爆出來：任務其實還在跑，本地卻什麼都沒留下。

拆開之後：進度看得到、被中斷不掉任務、重跑天然冪等（Submit 有記錄就不重送，Fetch 有 Note 就不覆寫）。這也正是 ADR-0004 的那條紀律——容器只做確定性的機械工作，**等待與判斷留在 agent 端**。

## Consequences

- 映像多裝一個 ffmpeg（約 150 MB）與一個 HTTP client 依賴，**要手動 rebuild**。
- 上傳前一律先問服務端的儲存狀態：超過單檔上限或剩餘空間不足就擋下不送。實測剩餘空間約 15 GB，幾場未轉檔的錄影就能吃光——這是先轉 mp3 再上傳的主要理由，不是為了省頻寬。
- **不刪除服務端的任務。** 刪了本地記錄就指向死 id，重抓的路也斷掉。改為在回報時附上剩餘空間，資源治理留給使用者。
- 語言參數寫死中文，不開 CLI flag。明確傳而不吃服務端預設，是為了不隨對方版本漂移。
- 圖片仍然排除，ADR-0005 不受影響。
- 服務端的 OpenAPI 契約留一份在 `api_info/openapi.json`，端點與欄位以它為準。它是對方產出的快照，服務改版時要重新抓一份。
